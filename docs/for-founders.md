# 给经营者：从“AI 说完成”到“有依据地交付”

## 一句话介绍

Agent + JEV Harness 帮助企业把可验证的小判断接进工作流程。第一版给 AI 助手增加开工分流和交付复核：先判断任务怎么处理，再检查完成声明有没有相应证据。

长期方向是将已跑通、规则稳定的重复工作固化为程序流程，JEV 只负责其中需要语义理解的判断。这个方向尚未在本项目落地，不能把第一版复核工具介绍成无人值守企业自动化。详见 [创始人演讲精读](founder-talk-reading.md)。

## 三个角色，用经营语言理解

| 角色 | 类比 | 实际职责 |
|---|---|---|
| Agent | 办事的同事 | 读资料、做计划、调用工具、制作结果、验证现场 |
| JEV | 回答小问题的检查员 | 在预先定义的选项中判断，提供概率信号 |
| Harness | 工作流程与检查规则 | 规定何时询问、怎样校验、何时补查、失败怎么继续 |

类比有边界：JEV 没有亲眼看你的系统，它只看 Agent 提交的摘要。摘要遗漏或错误，会影响判断。

## 三分钟分享话术

**第一分钟：为什么 Agent 需要 JEV Harness？**

“我们现在让 AI 做事情，它往往很快回答‘好了’。但经营者真正要确认的是：数字核对了吗，文件能打开吗，消息送到目标位置了吗？这些需要分别检查。我们想试一套小判断与检查流程，看能不能减少遗漏和返工；原有方法已经够用的地方就不用加。”

**第二分钟：它是什么，为什么这样设计？**

“Agent 负责理解和办事，JEV 回答限定范围的小问题，Harness 是把这些判断接入工作流程的规则。第一版先加两个环节：开工建议怎么处理，交付前对照完成声明和证据。这样可以把判断、计算、执行和授权分别放在合适的位置；模型不确定时也有明确的处理路径。”

**第三分钟：企业的经营者（创业者、老板）怎么用？**

运行 `python3 demo.py`。明确告诉听众：这是预设响应的离线教学演示，不是实时模型效果展示。屏幕显示日报有文件，但没有发送回执，因此需要补查。重点是让大家理解：生成、发送、送达是不同的状态，要分别提供证据。

说明经营者的使用顺序：选一件想交出去的工作，向 Agent 讲清楚要求和验收标准，给出必要资料与授权边界，先看建议和结果，再决定是否扩大。技术接入由 Agent 或技术伙伴协助完成。可复制 [试点任务卡](sme-playbook.md)。

结束时邀请对方选一个流程：“你公司哪件事最容易出现‘说做完了，但还得你自己去查’？先把这件事的验收标准写下来。”

## 从哪个场景起步

| 场景 | 可以问的小问题 | 程序或人必须掌握的事实 | 初版支持情况 |
|---|---|---|---|
| 日报交付 | 完成声明是否被证据摘要支持？ | 数据日期、口径、合计、实际送达回执 | 通用复核接口可用；业务连接器需另接 |
| 客服分流 | 售前、物流、售后，还是其他？ | 订单精确查询、是否退款、人工授权 | 未来场景，未实现 |
| 销售线索整理 | 是否有明确采购需求？ | 联系人许可、跟进记录、负责人的决定 | 未来场景，未实现 |

起步阶段只让它给建议，由人看结果。第一轮目标是发现它什么时候有用、什么时候会错。

## 第一周的试点安排

1. 选一个流程、一个负责人，写清楚“做完”的定义。
2. 准备 20–30 个有人工结论的脱敏样例，覆盖成功、失败、信息不足和服务异常。
3. 保留一部分从未用于调整提示或阈值的样例做验收。
4. 同时记录人工处理、规则检查与 JEV 辅助的结果和耗时。
5. 复盘漏掉了什么、误拦了什么、增加了多少工作量，再决定是否继续。

20–30 个样例只适合发现明显问题，不足以证明长期准确率。试点数量和时间是建议，不是本项目已发生的成果。

## 分享时不要做的承诺

不要承诺“接上就省 90% 成本”“不会幻觉”“95% 就可自动执行”。先问流程能否拆成小判断、有没有可查证的结果、错误由谁兜底。再根据你自己的试点数据谈收益。
